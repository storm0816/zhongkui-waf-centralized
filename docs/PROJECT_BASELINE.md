# 项目基线与维护标准

> 基线版本：`2.1.2`。本文件是 Zhongkui-WAF 后续设计、开发、发布和运维的统一准则；与旧说明存在差异时，以本文件和角色安装包说明为准。

## 1. 项目结论

Zhongkui-WAF 已完成从单机规则型 WAF 到可运营的 master/node 集群 WAF 的演进。当前架构适合继续稳定运行，后续工作应优先保证数据权威性、可观测性、发布可回滚和运维简单，而不是无边界叠加功能。

当前设计的合理点：

- 单机与集群模式边界清楚：单机沿用本地规则；集群由 master 统一控制。
- 集群规则、黑白名单和 CC 域名阈值有明确发布链路，避免 Node 各自维护不同版本。
- Node 不直连 MySQL 落业务统计；通过 Redis 上报，由 master 汇总，降低数据库连接和写入压力。
- 规则发布带版本、哈希、持久化快照和本地 LKG，能够处理重启、文件缺失、文件被截断和 Redis 短时异常。
- 管理台具备本地账号、LDAP、MFA、角色权限和操作审计；通知收敛为 IP 封禁事件，避免攻击日志刷屏。
- 完整包按 master/node 分角色构建，并将生产连接信息仅在构建时注入，源码仓库不保存真实环境密码。

## 2. 运行模式

| 模式 | 适用场景 | 规则来源 | 数据汇总 |
| --- | --- | --- | --- |
| 单机 | 小规模、独立部署 | 本地 `conf/` 文件 | 本机 Redis/MySQL 可选 |
| 集群 master | 管理与控制节点 | MySQL 已发布快照 | 汇总 Redis 并写入 MySQL |
| 集群 node | 业务防护节点 | Redis 快照，失败时使用本地 LKG | 仅上报 Redis，不直接汇总落 MySQL |

集群模式下禁止通过直接修改某台 Node 的本地规则来变更全局策略。本地规则文件只是运行镜像，下一次 master 对齐、重启或发布会以 MySQL 已发布版本恢复。

## 3. 数据权威与存储边界

| 数据类别 | 权威位置 | Redis 职责 | 本地文件/内存职责 |
| --- | --- | --- | --- |
| 集群规则、站点配置、IP 组、白名单、黑名单 | MySQL 已发布版本 | 快照发布与 Node 拉取 | master 运行镜像；Node 当前规则与 LKG |
| 集群 CC 域名阈值 | MySQL `waf_cc_domain_policy` | 下发阈值快照、分布式计数 | Node 按快照执行 |
| 集群域名及来源 Node | MySQL `waf_cluster_domain`、`waf_cluster_node_domain` | 域名实时请求/命中计数 | Node 从实际 Nginx `server_name` 观察后上报 |
| 攻击、封禁、流量、状态 | MySQL 归档/查询表 | 队列、dirty set、retry set 和短期缓存 | Node 产生事件与上报 |
| 会话、验证码、临时封禁、CC/反爬计数 | Redis | 实时权威 | Redis 故障时局部能力可退化到共享字典 |
| 系统连接配置、LDAP、钉钉、日志归档参数 | 每台机器的 `conf/system.json` | 不承担配置持久化 | 运行时加载与重载 |
| GeoIP MMDB | 本地文件 | 版本/校验状态上报 | Node 本地查询库 |

### 集群规则发布原则

1. 第一次初始化时，master 可从本地规则创建 MySQL 初始发布版本。
2. 此后 MySQL 是唯一规则权威；后台保存必须先持久化，再发布 Redis 快照。
3. master 启动、重启和周期对齐时，以 MySQL 已发布版本恢复本地文件和 Redis。
4. Node 校验版本与哈希后应用快照；Redis 不可用时保留当前内存规则与 LKG。
5. 规则、白名单、黑名单必须作为同一发布版本的一部分处理，禁止只手工改某一个载体。

### 集群域名与 CC 原则

- 域名只从 Nginx 实际选中的 `server_name` 发现，不信任客户端可伪造的 `Host`。
- 集群 CC 的计数维度为：`域名 + 客户端IP + CC规则`。
- 单机 CC 保持原有单机规则与本机计数逻辑，不与集群 CC 混用。
- 域名实时请求和 CC 命中统计保留 5 分钟；“24 小时访问”由小时桶汇总，仅用于运营观察，不作为审计数据。
- 来源节点是曾实际防护该域名的 Node 历史归属，长期保留。域名 24 小时未上报只标记为“已停用”；只有管理员删除该域名时，才清理域名、来源节点关联和 CC 特例阈值。

## 4. 防护与例外标准

- 白名单用于可信来源 IP 或网段；一行一个 `IP/CIDR + 可选备注`。白名单会在防护早期直接放行，配置前必须确认影响范围。
- 黑名单用于明确拒绝来源；自动封禁产生的临时状态由 Redis 管理，并写入 MySQL 封禁日志。
- 正常接口出现 SQLi/XSS 误报时，优先使用“规则例外白名单”，按 `域名 + 方法 + 路径正则 + 模块` 精确放行；不要关闭整个模块。
- `/token` 等机器接口若不应参与反爬/Bot/CAPTCHA，应使用 URI 精确排除；CC 是否参与由 CC 策略单独决定。
- 反爬虫、CC、人机验证和自动封禁必须分别配置、分别验证。页面总开关开启不代表每个子模块都开启。
- 钉钉只发送 IP 封禁通知；攻击日志仍写入 MySQL 和本地日志，不发送普通攻击告警。

## 5. 身份与权限标准

- 本地 `admin` 为初始超级管理员；至少保留一个可恢复的本地管理员账号。
- LDAP 用户首次登录自动创建，默认角色为 `readonly`；管理员可在后台调整 LDAP 与本地普通用户的角色。
- LDAP 绑定账号仅用于查询用户 DN，不等同于可登录的 LDAP 用户账号。
- MFA 支持全局强制和单用户强制；被单独启用 MFA 的用户应在下次登录完成绑定。
- 权限变更必须同时更新 MySQL 角色关联、当前会话权限判断和审计日志；前端展示不能代替后端鉴权。

## 6. 日志与归档标准

- Node 写 Redis 队列，master 批量写 MySQL；队列消费必须保持幂等与失败重试。
- `attack_log` 是热数据表。归档任务只在 master 执行，将超过保留天数的数据按周转入 `attack_log_archive_YYYYMMDD_YYYYMMDD`，再分批删除主表数据。
- 归档不是永久删除。归档表会持续增长，生产环境必须纳入 MySQL 容量、备份和长期保留策略。
- 当前推荐起点：保留 3~90 天热数据、每批 5,000 条、每 300 秒执行一次；应根据 MySQL IO、锁等待和积压量调整批次，而非盲目提高频率。

## 7. 配置、密钥与发布标准

### 配置边界

- Git 中的 `conf/system-master.json`、`conf/system-node.json` 只能保存脱敏模板和开发占位地址 `10.10.10.10`。
- 真实运行配置在目标机器 `conf/system.json`；升级不得覆盖它。
- 本机 SSH 测试连接只放在忽略的 `.zhongkui.private.env`。
- 构建生产包所需的 MySQL、Redis、LDAP、钉钉信息只放在忽略的 `.zhongkui.release.env`。
- 任何密码、Webhook、令牌、生产地址均不得写入源码、README、截图、提交信息或测试脚本。

### 发布流程

1. 修改代码、文档和版本号；确认前端、后端、数据结构和权限逻辑一致。
2. 在测试 master/node 上同步，执行 `nginx -t`、热重载和功能验收。
3. 构建 master/node 双包，校验 SHA-256，并确认包内没有 `.git`、私有配置、运行时 `system.json` 或开发目录。
4. 生产先备份 MySQL、Redis、运行时配置和规则，再使用对应角色包的 `upgrade.sh --role master|node` 升级。
5. 发布后核验节点版本、规则/白/黑/MMDB 状态、攻击日志入库、IP 封禁日志和钉钉通知。
6. 只有明确要求时才提交和推送 Git；禁止自动提交。

版本语义：破坏兼容性或架构切换使用主版本；新增可独立验收的能力使用次版本；修复、页面调整和兼容性改动使用修订版本。

## 8. 后续开发强制检查项

任何新需求在编码前必须明确以下内容：

1. 单机、master、node 三种模式分别如何工作；不适用的模式应隐藏页面入口或返回明确提示。
2. 数据权威是谁：MySQL、Redis、本地文件或共享字典只能有一个最终权威。
3. 数据生命周期：创建、更新、过期、恢复、删除和重启后的行为。
4. 前端展示、后端接口、权限校验、审计日志和发布同步是否同时完成。
5. Redis/MySQL 不可用时的降级和恢复行为，不能把“临时缓存”误当成永久数据。
6. 是否需要版本、哈希、幂等、锁、重试或回滚；集群共享状态必须考虑多 worker 和多节点并发。
7. 是否增加了敏感信息、生产地址、一次性脚本或无说明 Redis key；如有，必须先整理到正确位置并补文档。

## 9. 长期风险与改进优先级

以下不是当前上线阻塞项，但应在未来变更时优先处理：

1. **真实客户端 IP 信任边界**：当前防护依赖转发 IP 头。CDN/SLB 场景应配置可信代理网段，只接受可信代理写入的真实客户端 IP，避免公网伪造 `X-Forwarded-For`。
2. **归档表生命周期**：归档表不会自动永久清理，需要单独的数据保留、备份和恢复策略。
3. **管理接口规范化**：逐步统一业务响应为 `code=0` 成功，并抽取鉴权、响应和错误处理公共函数。
4. **后台前端模块化**：复杂页面继续增长时，将内嵌 JavaScript 拆为可复用模块，并保留接口契约测试。
5. **配置变更审计**：新增系统级配置时，明确其是否需要集群发布；不能默认所有 `system.json` 改动都会自动同步到所有 Node。

## 10. 基线验收

版本发布前至少完成：

- 单机：规则命中、白名单、黑名单、CC、反爬、日志写入。
- 集群：master 发布后 Node 规则/白/黑一致，master 重启后从 MySQL 恢复，Node 重启后从 Redis/LKG 恢复。
- 集群 CC：域名自动发现、默认阈值、域名特例、5 分钟命中、24 小时访问、停用标记和删除清理。
- 管理台：本地登录、LDAP 登录、角色调整、全局/单用户 MFA、只读权限不可修改配置。
- 告警与数据：封禁日志入 MySQL、钉钉仅收到封禁通知、攻击日志归档可执行且主表行数下降。
- 发布：角色包 SHA-256 正确、升级保留 `conf/system.json`，失败时可回滚。
